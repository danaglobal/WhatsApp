# Data Model: Admin Console and WhatsApp Coexistence Platform

**Feature**: `001-admin-console`  
**Database**: PostgreSQL 16 through Prisma migrations  
**Isolation rule**: Every tenant-owned row has a non-null `tenant_id`; access is protected by both tenant-scoped repositories and PostgreSQL RLS.

## Conventions

- Primary keys are UUIDv7 values generated by the application.
- Timestamps are `timestamptz` in UTC; externally supplied Meta timestamps retain the original provider value as well.
- Mutable entities carry `created_at`, `updated_at`, and an integer `version` for optimistic concurrency where races are plausible.
- External identifiers are stored as strings, never numeric types.
- Message content is encrypted at the storage layer and excluded from logs, traces, metrics, audit metadata, and error payloads.
- Tenant-owned foreign keys include `tenant_id` in a composite foreign key so a child cannot reference another tenant's parent row.
- User-visible list endpoints use stable cursor pagination, normally `(occurred_at, id)` descending.

## Platform and identity entities

### Tenant

| Field | Type | Rules |
|---|---|---|
| `id` | uuid | Primary key |
| `name` | text | Required, 1-160 characters |
| `status` | enum | `ACTIVE`, `SUSPENDED`, `CLOSED` |
| `suspended_at` | timestamptz? | Set while suspended |
| `closed_at` | timestamptz? | Set once closed |
| `content_delete_after` | timestamptz? | No later than 30 days after closure |
| `created_at`, `updated_at` | timestamptz | Required |

State transitions: `ACTIVE <-> SUSPENDED`; `ACTIVE|SUSPENDED -> CLOSED`. `CLOSED` is terminal. Suspension preserves and processes inbound data but blocks tenant operational access. Closure disables processing and schedules content deletion.

### User

| Field | Type | Rules |
|---|---|---|
| `id` | uuid | Primary key |
| `tenant_id` | uuid? | Null only for `SUPER_ADMIN` |
| `email_normalized` | text | Globally unique |
| `password_hash` | text | Argon2id encoded hash |
| `role` | enum | `SUPER_ADMIN`, `ADMIN`, reserved `AGENT` |
| `status` | enum | `INVITED`, `ACTIVE`, `DISABLED` |
| `last_login_at` | timestamptz? | Audit aid |

Phase-one invariants: each tenant has exactly one active or invited `ADMIN`; tenant admins cannot create invitations or users; `AGENT` is reserved in the enum but cannot be assigned by any phase-one API.

### Invitation and PasswordResetToken

Both store only a SHA-256 token digest, expiry, use timestamp, and issuing user/context. Invitations are restricted to the single tenant `ADMIN` created by a SuperAdmin. Tokens are single-use and invalidated transactionally.

### AuditEntry

Append-only record with `tenant_id` nullable for platform-only actions, actor ID/type, action, target type/ID, correlation ID, outcome, source IP digest, redacted JSON metadata, and `occurred_at`. Database permissions deny update/delete to runtime roles. Retained for 24 months, including after tenant closure.

## WhatsApp connection entities

### WhatsAppBusinessAccount

Tenant-owned representation of a Meta WABA: `id`, `tenant_id`, `meta_waba_id`, display name, business ID, status, and timestamps. `(tenant_id, meta_waba_id)` is unique.

### WhatsAppConnection

One linked phone number. Fields include `id`, `tenant_id`, `waba_id`, globally unique `meta_phone_number_id`, E.164 number, verified display name, `mode` (`COEXISTENCE` or `CLOUD_API_ONLY`), `status`, quality rating, messaging limit data, credential ID, connect/disconnect timestamps, and last webhook/sync timestamps.

State transitions: `PENDING -> CONNECTED`; `CONNECTED -> DISCONNECTED`; `DISCONNECTED -> PENDING -> CONNECTED`. Disconnect never deletes history. A reconnect reuses the logical connection when the Meta phone number ID matches, preserving message associations.

### MetaCredential

Tenant-owned envelope-encrypted secret record. It stores ciphertext, a unique 96-bit IV, authentication tag, wrapped data-encryption key, key version, scope metadata, expiry, and rotation timestamps. AES-256-GCM additional authenticated data binds tenant, credential ID, provider, purpose, and key version. Plaintext tokens are never persisted or returned by an API.

### ConnectionAttempt

Tracks every Embedded Signup session: `id`, `tenant_id`, initiating user, opaque state digest, configuration ID/version, requested onboarding mode, outcome (`STARTED`, `FINISHED`, `CANCELLED`, `ERROR`, `EXPIRED`), redacted session event, correlation ID, expiry, and completion timestamps. It contains no access token or authorization code after the server-side exchange.

### SyncRun and HistoryChunk

`SyncRun` represents the one-time coexistence `CONTACTS` or `HISTORY` request for a connection. It records eligibility deadline, consent/decline decision, request and completion times, state, counts, and failure category. A unique constraint prevents more than one successful request for each `(tenant_id, connection_id, sync_type)`.

`HistoryChunk` stores each received history payload before normalization with `sync_run_id`, phase, `chunk_order`, payload hash, encrypted/raw object reference, receive time, and processing state. `(tenant_id, sync_run_id, phase, chunk_order)` is unique. Normalization orders by phase and chunk order, not webhook arrival time.

## Messaging entities

### Contact

Tenant-owned contact scoped to one WhatsApp connection, with provider `wa_id`, normalized phone, optional profile name, sync source, and timestamps. `(tenant_id, connection_id, wa_id)` is unique.

### Conversation

Tenant-owned thread scoped to a connection and contact. Stores last-message ordering fields, unread count, and customer-service window start/expiry. `(tenant_id, connection_id, contact_id)` is unique. Cross-number search unions conversations within the authenticated tenant while retaining the connection ID on every result.

### Message

| Field group | Important fields and rules |
|---|---|
| Identity | `id`, `tenant_id`, `connection_id`, `conversation_id`, globally unique provider `wamid` when present, client idempotency key for sends |
| Direction/source | `INBOUND` or `OUTBOUND`; `CLOUD_API`, `SMB_ECHO`, or `HISTORY` |
| Content | message type, encrypted normalized content, reply/context IDs, media ID; never logged |
| Ordering | provider timestamp, ingestion timestamp, history phase/chunk/order, stable UUID tie-breaker |
| Delivery | current status, status rank, failure category/code, `delivery_unknown_at` |

Unique constraints cover `(tenant_id, connection_id, wamid)` and `(tenant_id, client_idempotency_key)`. Replayed live/history/echo events converge on the same logical row. Delivery states progress monotonically `QUEUED -> ACCEPTED -> SENT -> DELIVERED -> READ`; `FAILED` and `DELIVERY_UNKNOWN` are terminal operational outcomes unless later authoritative provider evidence advances the status. An ambiguous send timeout is not retried automatically.

### MessageStatusEvent

Immutable provider status observation keyed by a deterministic event digest. It records status, provider time, failure metadata, and source delivery. Reducers apply only status advances, making duplicates and out-of-order events harmless.

### MediaObject

Tenant-owned reference to downloaded media: connection/message IDs, safe generated object key, bucket, provider media ID, MIME type, byte count, checksum, scan state, encryption metadata, and download/expiry timestamps. Temporary Meta download URLs are never stored as the durable media location. Browser access uses short-lived backend-authorized signed URLs.

### MessageTemplate

Tenant-owned template keyed by `(tenant_id, waba_id, name, language)`. Stores category, normalized components, provider template ID, forward-compatible provider status string, rejection reason, and sync timestamps. Unknown future statuses are preserved and presented safely instead of causing ingestion failure.

## Ingestion and reliability entities

### WebhookDelivery

Durable receipt containing `id`, resolved `tenant_id` when known, payload SHA-256, exact raw body or encrypted object reference, signature result, provider object/field, receive time, correlation ID, processing state, attempt count, and error category. A unique delivery/event digest rejects exact replays. The API returns `200` only after this row and its outbox record commit.

### OutboxEvent

Created in the same transaction as durable state changes. Fields include tenant, aggregate, event type/version, redacted payload or object reference, availability time, publish attempts, and published time. A publisher sends it to BullMQ; a reconciliation sweep republishes stranded records.

### DeadLetter

Durable tenant-owned failure record for exhausted jobs: queue/job type, source entity, deduplication key, redacted input reference, attempt count, failure category, first/last failure times, resolution status, and operator notes. Retrying creates an audited new job rather than mutating history.

### RetentionRun

Records closure purge progress and audit-retention cleanup with scope, cutoff, counts, errors, and completion time. Content tables and object-store prefixes are deleted within 30 days after closure; audit entries remain for 24 months.

## Tenant isolation and RLS

The application role is `NOSUPERUSER`, `NOBYPASSRLS`, is not the table owner, and receives no direct policy-bypass grants. Migrations use a separate owner role. Tenant tables enable and force RLS with equivalent `USING` and `WITH CHECK` predicates against a transaction-local tenant context set through parameterized SQL. Repository methods require a `TenantContext`; raw Prisma access is unavailable to controllers and services. SuperAdmin cross-tenant screens use explicit, audited platform repositories and metadata-only views rather than disabling RLS.

Isolation tests MUST prove that selects, inserts, updates, deletes, nested includes, aggregates, background jobs, and websocket fan-out cannot cross tenant boundaries.

## Indexing and scale

- `Message`: tenant/connection/conversation time cursors; tenant/provider ID; tenant/client idempotency key; selective status indexes.
- `Conversation`: tenant last-message cursor and connection/contact lookup.
- `WebhookDelivery`, `OutboxEvent`, `DeadLetter`: state plus availability/receive time for workers.
- `AuditEntry`: tenant/time and actor/time.
- `Message` and high-volume event tables are partition-ready; initial production partitioning is selected from load-test evidence, with tenant hash partitions preferred to preserve isolation and spread large tenants.
- Dashboard totals come from incrementally maintained summary rows, not repeated scans of message history.
- Search in phase one is indexed metadata/contact/template search. Future message-content search must preserve tenant and number associations and requires a separately approved privacy/security design.
